[~2 min] Parkinson’s Law on Monday morning. Product, your question is “How long should this take?” We set performance targets for things like page load. Do the same for the most important user tasks. Decide how long they should take, and design to hit it. And for your own team’s work, timebox exploratory work so it can’t sprawl. Engineering, yours is “Can we prefill this?” Prefilling is the biggest lever we have on task time. Every field the system can fill from data we already have, a default, or the last entry, is time we hand back to the user. Notice how that connects back to Tesler’s Law. QA, your question is “How long did it take?” Time the core tasks on every release. Literally use a stopwatch. And if a task gets slower, even if it still technically works, treat it like any other regression and file a ticket. [Ask the room: “QA, would we even notice right now if our most common task got ten seconds slower?”] [Let one or two people answer.] That’s all four principles for this module. Let’s pull them together.
